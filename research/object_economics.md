# Object Economics

## Core Principle

> Objects are computational economic entities. They consume resources and produce value.

## Cost Structure

### Per-Object Costs

| Cost Type | Unit | Typical Value | Control |
|-----------|------|---------------|---------|
| Reasoning | $/token | $0.000001–$0.00003 | Model tier, batching, caching |
| Storage | $/GB/month | $0.10 | Compression, archiving |
| Compute | $/CPU-hour | $0.01 | Dormancy, local models |
| Network | $/GB | $0.01 | Relationship locality |
| Latency | seconds | 0.1–5 | Async processing, pre-filtering |
| Risk | $/incident | Variable | Constraints, sandboxing |

### Value Structure

| Value Type | Unit | Measurement |
|------------|------|-------------|
| Action value | $/action | Revenue, cost savings, risk reduction |
| Information value | $/bit | Decision improvement from information |
| Learning value | $/lesson | Future behavior improvement |
| Relationship value | $/connection | Network effects, coordination |

---

## Object Utility Function

```
U(object, t) = Σ_{τ=t}^{∞} [V(action_τ) × γ^{τ-t}] - Σ_{τ=t}^{∞} [C(τ) × γ^{τ-t}]
```

Where:
- V(action_τ) = value generated by action at time τ
- C(τ) = cost at time τ
- γ = discount factor (0.9–0.99)

### Simplified Form

```
U(object) ≈ average_daily_value × expected_lifetime - total_cost
```

### Runtime Decisions Based on Utility

```
U > threshold_high:   Keep active, increase budget
U > 0:                Keep, maintain current level
U < 0:                Archive or retire
U < threshold_low:    Immediate retirement
```

## Internal Economy (Optional Advanced Feature)

### Currency: "Cognits"

Objects earn cognits by:
- Generating valuable actions
- Providing useful information to other objects
- Discovering insights
- Running successful experiments

Objects spend cognits on:
- Reasoning (pay per token)
- Communication (pay per message)
- Object creation (pay to spawn children)
- Memory storage (pay per byte)

### Budget Allocation

```
Initial budget: developer-assigned or system-generated
Earnings: based on measured value
Subsidies: system provides base budget to prevent starvation
Taxes: system takes cut to fund shared infrastructure
```

### Market Dynamics

```
High demand for reasoning + limited supply → price increases
Low demand + high supply → price decreases
Objects adjust behavior based on price signals
```

**Note:** Internal economy adds significant complexity. Start with simple budgets. Add market dynamics only if simple budgets fail.

## Value Measurement

### Direct Measurement

```
Object: CustomerRetentionBot
Action: Recommended discount to at-risk customer
Result: Customer stayed (vs. predicted churn)
Value: Customer LTV × retention_probability_lift
```

### Indirect Measurement

```
Object: DataQualityMonitor
Action: Detected anomaly in sales data
Result: Data team fixed issue
Value: Estimated cost of bad decision avoided
```

### Difficult Measurement

```
Object: ExperimentRunner
Action: Ran A/B test on website layout
Result: No significant difference
Value: Learning that layout doesn't matter (saves future experiments)
```

**Key insight:** Not all value is directly measurable. Some value is informational (learning) or relational (coordination).

## Cost Optimization Strategies

### 1. Model Tier Selection

```
If task is routine AND confidence is high:
    use local 8B model ($0)
If task is novel OR confidence is medium:
    use cheap API ($0.001/1K)
If task is critical OR confidence is low:
    use frontier model ($0.03/1K)
```

**Savings:** 50–100×

### 2. Batching

```
10 objects need reasoning → 1 batched API call
Cost: 1 × overhead vs. 10 × overhead
Savings: 2–10×
```

### 3. Caching

```
Similar context → cached result
Hit rate: 30–70% for repetitive domains
Savings: 30–70%
```

### 4. Dormancy

```
Dormant object: $0 compute, $0.000001 storage
Active object: $0.01–$1 compute/day
Ratio: 1:10,000 to 1:1,000,000
```

### 5. Retirement

```
Old object with no relationships and no recent value:
    Archive state ($0.000001 storage)
    vs. Keep active ($0.01/day)
Savings: 10,000×
```

## Economic Viability Checklist

For a system with N objects:

1. **Value per object > $0.01/month?**
2. **Cost per object < $0.01/month?**
3. **Active fraction < 1%?**
4. **Model tier strategy implemented?**
5. **Retirement policy active?**
6. **Batching + caching enabled?**

If all yes: economically viable.
If any no: investigate and fix.

---

## Conclusion

**Object economics is not a theoretical concern. It is a design constraint.**

Every design decision (dormancy, tiered models, batching, retirement) must be justified by economic impact.

**The simplest viable economic model:**
- Each object has a daily token budget
- Budget is spent on reasoning, communication, experiments
- If budget exhausted: object uses deterministic behavior until next day
- Objects with consistently negative utility are retired

This is sufficient for Phase 3. Advanced internal economies (cognits, markets, auctions) are Phase 5+.
